# PokerLens

Paste a No-Limit Hold'em hand history and get a street-by-street review: equity against an estimated range, pot odds, EV of calling, a verdict per decision, and an AI coach that explains the hand in plain English.

## What it does

- **Parses** PokerStars, GGPoker and 888poker hand histories (cash and tournament, antes, all-ins, uncalled bets). The site is detected from the header and every format becomes the same parsed hand, so review, coach and session report do not know which site a hand came from. GGPoker follows the PokerStars layout with a letter prefix on the hand id and a "Dealt to" line for every player; for a run-it-twice hand the first board is reviewed and both halves of the pot are counted. 888poker writes a raise as the chips put in by that action, never marks an all-in and never writes an uncalled bet, so the parser derives the raise total, the all-in and the returned chips from the stacks. A dead blind is split into dead money and a live big blind. `tests/hand-formats.test.ts` writes the same hand in all three formats and checks they parse to the same hand and get the same review.
- **Replays** the hand on a table with a step-through timeline.
- **Analyses every hero decision**: Monte Carlo equity against each opponent's range with card removal, pot odds, EV of calling, SPR, bet size and bluff break-even frequency. With cards to come, calls and folds are judged on realised equity (raw equity times a factor for position and hand shape, `src/lib/poker/realization.ts`), and the raw figure is shown next to it. After the flop, heads-up, each decision also gets the EV of betting or raising compared with checking, calling or folding: hero's own size, or two thirds of the pot (a raise to three times the bet) when hero was passive (`src/lib/poker/raise-ev.ts`). On the river that EV decides two verdicts: a medium-strength bet that gains is a thin value bet, and checking back when a bet gains is missed value with its EV lost.
- **Estimates opponent ranges** from position and preflop action using simplified 6-max charts with mixed frequencies on borderline hands (a hand played more than one way is in each range at its share), and a second set for effective stacks of about 15-40bb, chosen per player from the starting stacks, then reweights them after each postflop bet, call or check. Ranges are editable, and an opponent profile (rarely bluffs / standard / bluffs a lot) shifts the estimate for exploitative review.
- **Explains** the hand with an LLM coach that only sees the computed numbers, with follow-up questions.
- **Trains preflop ranges** at `/train`: a seat, the action so far (first in, facing an open, opened and facing a 3-bet) and a hand; pick raise, call or fold and see the full 13x13 range for the spot with one sentence on why. The deal favours hands near the edge of each range, missed spots come back after a few hands (Leitner boxes counted in answers), and accuracy is recorded per position in `localStorage`.
- **Solves river spots** at `/solver`: a CFR+ solver for heads-up rivers takes two ranges, a pot, a stack and up to three bet sizes, and returns a Nash equilibrium. It shows the mixed strategy and EV of every combo, the value-to-bluff split of each bet, defence frequency against the minimum defence frequency, and how far the answer still is from equilibrium. Pick an opponent leak (bluffs too little or too much, calls or folds too much) to see the best response and what it gains.
- **Solves push/fold for short stacks** at `/pushfold`: pick a stack depth (1 to 20bb), a table size, the shover's seat and an ante, and see the equilibrium shoving range and each caller's calling range on the 13x13 grid. The ranges are solved in the browser with CFR+ over the 169 starting hands, from a checked-in table of exact hand-versus-hand all-in equities. Hand review uses the same solver for preflop decisions with about 15bb or less: hero's own shove (or fold when first in) is judged by its chip EV against equilibrium callers, and an opponent's shove or reshove gets an equilibrium range instead of a 100bb chart range. Each such verdict names the model it came from.
- **Reviews whole sessions** at `/session`: paste or upload a file with many hands from PokerStars, GGPoker or 888poker (one file can mix them). It is split on hand headers and each hand is parsed on its own, so a hand that cannot be read (or a duplicate) is listed with its reason and the rest still import. Every hand goes through the same hand review, and the report shows EV lost by spot type (preflop unopened, facing an open, facing a 3-bet, facing a 4-bet or more, short-stack push/fold, flop or turn first to act or facing a bet, river first to act or facing a bet), verdict counts, EV lost per 100 hands next to the actual result, the ten biggest single mistakes (each opens its full review), and VPIP, PFR and 3-bet with their opportunity counts and a 95% Wilson interval. A sample session of 211 hands can be loaded without a file. The engine is `src/lib/poker/session.ts`; the page runs it in a Web Worker with a progress bar.
- **Guided tour**: "Take the guided tour" on the home page walks through every feature on its real page in twelve steps (hand import, a decision verdict, the opponent range, the coach, the range trainer, the river solver, push/fold, the session report, the integrity lab, the demo hands, Learn, and metrics, monitoring and the changelog). Each step highlights the part of the page it is about and says what it does and why it matters for player study or game integrity, with a link to the page. It can be left at any step (Skip, Escape, or the page link), moved with the arrow keys, and works at 375px. The current step is only the `?tour=N` query parameter, so nothing is stored. Steps are defined in `src/lib/tour.ts` and point at elements marked `data-tour`; `tests/tour.test.ts` fails if a page has no step, a step's page does not exist, or its element is not marked. Events: `tour_started`, `tour_step_viewed`, `tour_finished`, `tour_left`.
- **Demo hands** at `/demo`: three sample hands with a short walkthrough of each, written to be explained aloud. The river lead teaches pot odds and bluff-catching (the fold is wrong under every opponent profile), jacks against a 4-bet jam shows range narrowing and how a slightly wider range flips an exact all-in verdict, and KQ suited against a short-stack reshove shows a push/fold equilibrium used instead of a 100bb chart, with its limits. Each step that needs a change in the app (a profile, a range) says which. The scripts live in `src/lib/demo-hands.ts`; `tests/demo-hands.test.ts` runs them through the coach-evaluation number checker against the engine's fact sheet for that hand (after the step's change), and checks the verdicts each script argues for, so the scripts cannot drift from what the app shows.
- **Integrity lab** at `/integrity`, a prototype on synthetic players: for one player's hands it shows the distribution of EV lost per decision and of postflop bet sizes next to a baseline of eight simulated humans, and raises two signals. "Close to the engine" means the player took the higher-EV option more often, and lost less per decision, than every baseline human, which is how real-time assistance would show up. "Uniform bet sizing" means one size band is used more than by any baseline human, which is how a simple bot shows up. Three players can be inspected: a regular (built like the baseline but not part of it), an assisted player that asks this app's engine before every call or fold, and a bot that always bets half the pot. The engine is `src/lib/poker/integrity.ts`.
- **Accounts and saved hands** (Supabase auth, row-level security): save a reviewed hand with its assumptions, reopen it later, and see recurring leaks and total EV lost across saved hands.
- **Usage instrumentation**: anonymous product events (`hand_analyzed`, `decision_viewed`, `range_edited`, `profile_changed`, `coach_requested`, `hand_saved`, `trainer_answered`, `solver_run`, `solver_leak`, `pushfold_viewed`, `session_imported`, `session_analyzed`, `session_hand_opened`, `demo_hand_opened`, `integrity_player_viewed`, `tour_started`, `tour_step_viewed`, `tour_finished`, `tour_left`) go to a write-only `events` table. No hand text or personal data is recorded in events.
- **Shows the usage funnel** at `/metrics`, a private page: per anonymous session, how many reached hand analysed, then range edited, then coach requested, then hand saved, with conversion from the previous step and from the first, over the last 24 hours, 7, 30 or 90 days. Below it are raw event and session counts for every event name the app sends, plus any retired names still in the table. The aggregation is a pure function in `src/lib/metrics.ts`.

## What it is not

Hand review is not a solver. The preflop charts approximate published solver charts but were not solved here: the mixed frequencies and the 15-40bb set are hand-written estimates, and between 15bb and 40bb they are coarse. A preflop action the chart takes at least 25% of the time counts as good; less than that is "ok". Postflop range narrowing is a documented heuristic. Equity realisation uses rules of thumb (1.0 in position; 0.85 on the flop and 0.92 on the turn out of position; 0.8 preflop out of position, adjusted for suited connectors and offsuit gappers), not solved values, and is 1 when no more betting can follow, so river and all-in verdicts stay exact for the assumed range. The EV of betting or raising assumes the opponent defends exactly the minimum defence frequency with its strongest hands (made-hand strength, with strong draws one step up), never re-raises, and checks the hand down after calling; before the river it is shown as a rough guide only. ICM and rake are not modelled. The range trainer drills the 100bb charts and accepts any action the chart takes at least 25% of the time.

The river solver is exact only for its model: two players, the ranges and bet sizes entered, at most one pot-sized raise, no rake. Ranges are entered by hand class, so suit combinations of a hand start with equal weight. It is not yet wired into hand review, which would need an estimate of hero's own range.

Push/fold ranges are exact only for small blind against big blind (one shover, one caller), and only as a shove-or-fold game: chip EV with no ICM, no limping and no min-raising, which real play prefers for many hands above roughly 10bb. With more players left to act it is an approximation: at most one player calls (no three-way all-ins), callers' cards are treated as independent, and everyone is given the same stack on the `/pushfold` page. A reshove over an open is solved against the opener's chart range with only the opener able to call, so it is an estimate too. Folded players' cards are ignored throughout. In hand review a small raise or limp with a short stack is still judged by the 100bb chart, with a note saying what the push/fold model would do.

The session leak report inherits every assumption of hand review: its EV figures are only as good as the estimated opponent ranges. EV is counted only where hand review computes it (calls and folds against a bet, push/fold spots, and river bets and checks judged by the EV of betting), so chart deviations and betting choices before the river are flagged without an EV figure and the total understates what they cost. A river call or fold, or an all-in, is exact for the assumed range; everything with cards to come ignores implied odds. Sessions use 1,000 Monte Carlo samples per decision instead of 4,000 to stay fast, so opening a hand from the report can show a slightly different figure. VPIP, PFR and 3-bet follow the usual tracker definitions: walks are left out, checking the big blind is not VPIP, and a 3-bet opportunity is facing exactly one raise with chips left to re-raise, counted once per hand. The counts are exact; the page warns under 100 hands and flags any stat with fewer than 30 opportunities. Cash hands take a few milliseconds each; short-stack tournament hands take about 0.3 seconds each because hand review solves a multiway push/fold game for them. PokerStars, GGPoker and 888poker are read; other sites (Winamax, iPoker, partypoker) are not yet, and only No-Limit Hold'em is supported. The 888poker and GGPoker layouts are based on public examples of their exports, not on files from an account, so an unusual line (a straddle, a GGPoker cash-out) is ignored rather than understood.

The sample session is generated by `src/lib/poker/sample-session.ts`, a small seeded simulator: 200 6-max cash hands and 10 short-stack tournament hands, with villains playing the app's charts and a strength-based postflop policy, and a hero with leaks built in (calls opens too wide, folds too much to 3-bets, folds medium hands to river bets, calls river bets with busted hands, shoves too tight when short). Pots are kept heads-up after the flop and rake is zero. One hand is deliberately broken to show how import errors are reported. `tests/session.test.ts` checks that the report finds those leaks.

The coach evaluation checks numbers, not meaning. It finds every quantity in a reply (percentages, big-blind amounts, combo counts, ratios such as 2:1, sizing multiples such as 3x, decision references such as #4, bare numbers) and requires the same value with a compatible unit on the fact sheet; a number with a unit may be rounded to fewer decimals ("about 14bb" for 14.2bb), a bare number must match exactly. Cards, hand classes and range notation (7h, 99, 76s, A5s-A2s), "3-bet", "6-max", "7-high", "Kx" and ordinals are not quantities and are skipped. So a reply still passes if it puts a real number in the wrong place (calling the pot odds the equity), gets a sign or a comparison wrong, or reasons badly; signs are ignored because the sheet and the prose word gains and losses differently. A bare number is accepted if any number on the sheet has that value, so a coincidence can hide an invented one, and a pocket pair written without a unit ("99") is read as a hand, not a number. Numbers written as words ("half pot", "two to one") are not checked. The recorded replies are written by hand, so `npm test` proves the checker and the fact sheets, not the model; the live run checks the model, but only for the one reply it happens to give.

The integrity lab is a prototype and every player in it is simulated, by the same seeded simulator as the sample session (`makeStyledSession` in `src/lib/poker/sample-session.ts`, whose hero style is now a parameter; the sample session itself is unchanged and a test pins it). EV lost is measured against this app's engine, not a solver, and only on calls and folds facing a postflop bet, the one place the engine knows the EV of both options; bets, checks, raises and preflop play are not scored. Agreeing with the engine therefore means agreeing with its heuristic range estimates. The baseline humans differ only in how big their built-in leaks are and in random sizing noise, so the baseline is far narrower than a real player pool and the flags are much cleaner than they would be on real data. A flag needs the player to be outside the whole baseline range and at least 30 measured decisions or 20 bets. The assisted player is also flagged for sizing, because its tool offers a few solver-style sizes; that is a choice in this simulation, not a general rule. Strong honest players agree with good models too, so on real data these would be reasons to look, alongside signals the app does not have (timing, session patterns), never proof.

The metrics page counts sessions, not people: a session is one browser tab's random id in session storage, so a new tab or a new visit counts again, and signed-in users are not joined across devices. A funnel step counts a session only when it fired that event after reaching the step before (time order, row id breaking ties); a session that skips a step stops there, and a second figure shows how many sessions sent the event at all. Only events inside the window are read, so a session that started before the window opened can be missing its early steps. Events are sent from the browser without retries, so ad blockers and failed requests make every figure a lower bound. A page view reads at most 50,000 events and says so when it hits that limit; aggregation runs in the app rather than in SQL, which is fine at this traffic but would move into a database view at scale. The page itself records no events.

## Design decisions

- **The maths is deterministic code; the LLM only explains.** `/api/coach` re-runs the analysis on the server and sends the model a fact sheet. The prompt forbids it from producing its own numbers.
- **Seeded Monte Carlo**, so the same hand always gives the same output. The trainer's deal is seeded the same way: the next spot is a pure function of the stored progress.
- **The solver is checked against a closed-form answer.** `tests/solver.test.ts` solves the textbook nuts-or-air game at three bet sizes and compares bluff share, calling frequency and EV with the known equilibrium, then checks properties any equilibrium must have on a real spot (EVs sum to the pot, the nuts never fold, equilibrium play never loses to a leak, the best response never does worse).
- **Preflop equities are enumerated, not sampled, and checked in.** `scripts/preflop-equity.ts` runs every five-card board through the evaluator for all 14,196 pairs of starting-hand classes and writes `src/lib/poker/preflop-equity-data.ts`. That takes minutes, so it is done once rather than at page load; the push/fold solver then needs only table lookups and solves a spot in well under a second.
- **Push/fold is checked against the published chart and against the definition of an equilibrium.** `tests/pushfold.test.ts` compares shove and call thresholds with the HoldemResources heads-up Nash chart, recomputes every hand's EV independently to confirm that no single hand can gain by switching action, and checks that the calling range is exactly what pot odds allow against the shoving range.
- **Session stats are checked on hands built by hand.** `tests/session.test.ts` builds nine hands whose VPIP, PFR and 3-bet are known by construction (an open, a fold, a walk, a limp, a 3-bet, a flat, a fold to an open, an open that folds to a 3-bet, a checked big blind), and checks that EV lost by spot type sums to the total, that a broken hand is reported while the rest import, and that the same file always gives the same report.
- **Validation scenarios** in `tests/validation.test.ts`: hands where the right answer is not in dispute, plus consistency properties (wider range means more equity, more bluffs means a bluff-catcher gains equity, EV sign matches equity versus price). A change that flips one of these has made the output strategically inconsistent. `tests/trainer.test.ts` does the same for the trainer: every dealt spot agrees with the charts and with the hand review, AA always raises, 72o always folds, opening ranges only widen towards the button, and a missed spot is always scheduled sooner than one answered correctly.

- **The events table stays write-only for browsers.** No row-level security policy was loosened and no migration was needed. `/metrics` reads the table on the server with the Supabase secret key (`SUPABASE_SECRET_KEY`, no `NEXT_PUBLIC_` prefix, in a `server-only` module), selecting only the event name, session id and time, never props or user ids. The page is behind HTTP Basic auth with `METRICS_PASSWORD`: `src/proxy.ts` asks for it and the page checks it again before reading anything. With no password set the page reads nothing and says metrics are switched off; with no secret key it names the missing variable. Both are read at request time, so the build passes without them. The page is not linked from the app's header and is marked `noindex`.
- **Coach evaluations are deterministic by default.** The rule that the coach only explains the engine's numbers is checked in `tests/coach-eval.test.ts` by `src/lib/coach-eval.ts`, which lists the numbers in a reply and reports any that are not on the hand's fact sheet. `npm test` runs it over fixed replies in `tests/fixtures/coach-replies.ts`: for each sample hand, one grounded review in the prompt's format that must pass, and replies that each break the rule in one way (a margin the coach worked out itself, pot odds as a ratio, an extra decimal, an outs count, a recommended bet size, an ICM adjustment) and must be flagged with exactly that number. It also checks the built-in summary shown when there is no API key, which found that the summary counted flagged decisions while the fact sheet did not, so the sheet now states that count. Calling the model in `npm test` would make it slow, cost money, need a key and give a different answer each run, so the live check is opt-in: `COACH_EVAL_LIVE=1 npx vitest run tests/coach-eval.test.ts` sends every sample hand to the model with the same prompt as `/api/coach` (shared through `coachRequest` in `src/lib/coach.ts`), reading `OPENAI_API_KEY` from the environment or `.env.local`, and prints any reply that fails.
- **The integrity lab is precomputed and checked for drift.** Simulating and analysing 1,500 hands for each of eleven players takes about 15 seconds, too slow for a page load, so `scripts/integrity-lab.ts` writes the result to `src/lib/poker/integrity-data.ts`, as is done for preflop equities. Only hands where the player acts after the flop are analysed, since both signals come from there. `tests/integrity.test.ts` recomputes one baseline human and the bot and fails if the checked-in data differs, checks that the stored baseline and signals follow from the stored profiles, and checks the expected outcome: the assisted player is flagged as close to the engine, the bot only for sizing, and the regular for nothing. It also unit-tests EV lost per decision and the flag rules, including "too few hands" on small samples.
- **The funnel is tested on hand-built event lists.** `tests/metrics.test.ts` covers step order, a session that skips a step, ties in time, sessions kept apart, empty windows, window edges, every event name being listed, and that the same rows in any order give the same output.

## In production

- **Deployment.** Vercel builds every push: each pull request gets a preview URL and merging to `main` deploys production at https://pokerlens-gold.vercel.app. Environment variables are set in the Vercel project: `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (accounts, saved hands, events and error reports), `OPENAI_API_KEY` (the coach; without it the built-in summary is shown), and `SUPABASE_SECRET_KEY` with `METRICS_PASSWORD` (the private metrics page and server error reports). Every one is optional and the app says what is switched off.
- **CI.** `.github/workflows/ci.yml` runs `npm run lint`, `npm test` and `npm run build` on every pull request and on `main`, so a change is checked even when nobody runs the commands locally.
- **Release.** `src/lib/release.ts` takes the short commit Vercel built (`VERCEL_GIT_COMMIT_SHA`, or `dev` locally). It is in every page footer, in `/api/health` and on every error report, so a report points at one commit.
- **Health check.** `GET /api/health` returns `200` with the release, the environment and which optional services are configured (never their values), for an uptime monitor.
- **Error monitoring.** Errors go to an insert-only `app_errors` table (`supabase/migrations/20261114000000_create_app_errors.sql`), the same pattern as `events`: browsers may insert client errors only, and the metrics page reads the table on the server with the secret key. Browser errors are caught three ways: uncaught exceptions and unhandled promise rejections in `src/instrumentation-client.ts`, and render errors in `src/app/error.tsx` and `src/app/global-error.tsx`, which show a friendly page with a retry button and a reference. Server errors from rendering, route handlers, server actions and the proxy are caught by `onRequestError` in `src/instrumentation.ts`, logged to the Vercel function logs and stored with the secret key. A report holds a message of at most 500 characters, at most eight stack frames, the page path without its query string, the release and the anonymous visit id; query strings, e-mail addresses and runs of nine or more digits are scrubbed (`src/lib/errors.ts`), and a visit sends at most one report per distinct error and ten in all. The metrics page groups reports by fingerprint (the message with numbers removed plus the first stack frame without line numbers) with counts, sessions, paths, releases and first and last seen. A hosted service such as Sentry would add source maps, alerts and release health; this keeps error data in the project's own database with no new vendor, and `reportClientError` and `reportServerError` are the two places to swap one in.
- **Changelog.** `/changelog` lists what shipped, newest first, with the pull request for each change and a "What we learned" note where something found after shipping changed the app. It is written in `src/lib/changelog.ts`, and `tests/production.test.ts` fails if a ticked roadmap item has no entry.

## Layout

- `src/lib/poker/` engine: `cards`, `evaluator`, `ranges`, `charts`, `equity`, `parser`, `analyze`, `realization` (equity realisation), `raise-ev` (EV of betting and raising), `trainer`, `solver`, `solver-spots`, `pushfold`, `preflop-equity-data` (generated by `scripts/preflop-equity.ts`), `session` (import and leak report), `sample-session` (simulated demo session and synthetic players), `integrity` (integrity lab signals), `integrity-data` (generated by `scripts/integrity-lab.ts`)
- `src/lib/coach.ts` fact sheet and prompt, `src/lib/coach-eval.ts` checks that a coach reply only states numbers from the fact sheet
- `src/app/api/coach/route.ts` streaming coach endpoint
- `src/components/` UI
- `src/workers/session.worker.ts` runs a session analysis off the main thread
- `src/lib/supabase.ts`, `src/lib/track.ts` accounts, saved hands, usage events
- `src/lib/metrics.ts` funnel aggregation, `src/lib/metrics-data.ts` server-only events read, `src/lib/metrics-auth.ts` password check, `src/proxy.ts` password prompt for `/metrics`
- `src/lib/event-names.ts` the list of event names
- `src/lib/demo-hands.ts` the demo walkthroughs, shown at `/demo`
- `src/lib/trainer-store.ts` trainer progress in `localStorage`
- `src/lib/errors.ts` error reports and grouping, `src/lib/report-error.ts` and `src/lib/report-error-server.ts` send them, `src/instrumentation-client.ts` and `src/instrumentation.ts` catch them, `src/app/error.tsx` and `src/app/global-error.tsx` error pages
- `src/lib/tour.ts` the guided tour's steps, `src/components/Tour.tsx` its panel and highlight
- `src/lib/release.ts` the deployed commit, `src/app/api/health/route.ts` health check, `src/lib/changelog.ts` the changelog shown at `/changelog`
- `.github/workflows/ci.yml` lint, test and build on every pull request
- `supabase/migrations/` schema and row-level security policies

## Run

```bash
npm install
cp .env.example .env.local   # add OPENAI_API_KEY and the Supabase URL and publishable key
npm run dev
npm test
```

Apply the migrations in `supabase/migrations/` to the Supabase project (the `app_errors` table is new; without it error reports are dropped quietly). To see `/metrics`, also set `SUPABASE_SECRET_KEY` (Supabase dashboard, API keys, a secret key) and `METRICS_PASSWORD` in `.env.local` or the host's server environment, then open `/metrics` and enter the password with any user name.
